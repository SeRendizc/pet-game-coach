\section{协作中的难点}

这道题我用 AI 编程助手实现，分工与产品里的分工是同一个形状：助手产出实现与说法，我负责判断它对不对。项目的主线是「把算和说分开」，开发过程里同一条原则又出现了一次，只是「算」换成了\textbf{验收}。

\subsection{「测试全绿」不能当验收}

全项目出现最多的一类问题是：代码看着对、测试全绿、功能根本没有生效。四个实例：

\begin{itemize}[leftmargin=1.5em,itemsep=0.12em,topsep=0.25em]
\item 服务端静态资源白名单漏了新模块 \code{rules.js}，\code{/rules.js} 返回 404，\code{app.js} 的 import 图整体失败，\textbf{整页白屏}。
\item 陪练的 \code{notify()} 有定义，全仓库没有一个调用点。主动气泡写完了，从不出现。
\item 军师改造留下一个未定义变量，每秒抛一次 \code{ReferenceError}，浏览器日志里攒了 75 条。
\item 敌方补位「决定了却无人提交」：助手选好了合法换宠、存进变量就返回，而玩家那条路径又拒绝替它提交，界面永久冻结在「正在出招…」。
\end{itemize}

四次都不是粗心，而是测试的对象选错了：单元测试测的是「这个函数算得对不对」，不测「这个函数有没有被接上」。这四次没有一次是读代码读出来的，全部是实际跑起来才看见的。

所以我把验收换成了两层可复现的检查。第一层是 \path{wiring.test.js}，离线、确定性，只查接线：\code{app.js} 里每个 \code{\$('id')} 都必须在 \code{index.html} 或 \code{app.js} 自建的元素里存在；死函数清单必须恰好是两个已知遗留；面试题要求的每项能力都必须在 \code{app.js} 里找得到入口。它第一次运行就找出一处指向已删除元素的残留引用。第二层是冒烟测试，用无头浏览器真打一局训练赛，断言营地渲染出伙伴卡、对局能打到结果、控制台零报错；它不进 \code{npm test}，因为需要浏览器的检查不该当成必过门。这一层也有抓不到的东西，我自己见过一次假阳性：测试报出「最长连续无可点 14 次」，看上去快卡死了，查下去是它从未设置播放速度，每一回合都在放动画、按钮本来就处于禁用状态——这个指标量的是动画时长，不是死锁。

\subsection{不会失败的检查比没有检查更糟}

检查本身也需要被检查。玩家文案的术语检查写出来之后，我做了负向验证：把禁止词表里的词植入一句玩家可达的文案，测试必须失败；移除，测试必须通过。这一步让一个原本看不出来的缺口暴露了——检查取局内提示时没有传事件参数，于是「明显策略错误」那条理由对应的正文根本不在覆盖范围内。我第一次修补的方向也是错的：手工造一个事件参数传进去，负向验证立刻戳穿，把违规词放回源码，检查照样通过——那段正文要等枚举真的算出一次事故才会生成。最后换成静态扫描，逐行取 \code{coach/} 下的中文字面量对词表，不依赖任何运行时路径；它随即又扫出四处运行时检查没覆盖到的真泄漏。结论很短：\textbf{每一条「已修复」都必须能指出哪个检查会因为它变红}。

\subsection{口径错误比代码错误更难发现}

有一处缺陷代码完全正常，错的是统计口径：玩家补位的那一回合本来就不该出招，却被计成一次「引擎兜底」，方向恰好让对手 agent 显得比实际更差。测量本身也会说谎，而它说谎的时候不会有测试失败。同类的一处是犹豫判定用了墙钟时间，玩家中途去操作对方面板的 13 秒被算成「犹豫了 13 秒」。

\subsection{哪些判断我不外包}

助手给的是数与文本，结论由我做。有一次我看到一份评测结果文件存在，就以为真实模型评测已经跑完，打开只有两行，是更早一次局部验证的残留；此后我逐条看实际数据，不看文件名。另一类更容易漏：助手给出的「某方案没用」往往只对了一半——检索实验里最好的一臂确实没有显著赢过基线，但拆开四条臂能看到排序指标变好了。这两件事指向同一条纪律：结论和代码一样需要验收，而验收的地方只能是产物本身。
