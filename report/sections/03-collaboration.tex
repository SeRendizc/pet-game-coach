\section{协作与验收}

分工是清楚的：\textbf{我负责顶层设计、真实使用与验收，子 agent 负责具体实现和代码层面的测试。}架构、三种角色的边界、每条约束的判据由我定，单元测试交给子 agent 写，可以并行推进。代价是「实现完了」和「功能生效了」是两回事——单元测试能验证一个函数内部对不对，验证不了这个函数有没有被接上，也验证不了它量的是不是该量的东西。这一章里的问题都是这么漏出来、又被我一个个测出来的。

\subsection{代码是对的，功能没有生效}

同一个形态我碰到三次：代码看着对、\code{npm test} 全绿、功能根本没有生效。

\begin{itemize}[leftmargin=1.5em,itemsep=0.12em,topsep=0.25em]
\item 新增的模块 \code{rules.js} 没有进静态资源白名单。仓库里的白名单、测试、模块图全是对的，但我打开页面看到的还是白屏：运行中的那个进程拿的是旧白名单，\code{/rules.js} 返回 404，\code{app.js} 的 import 图整体失败，页面一行 JS 都不执行。单元测试只能验证磁盘上的文件，验证不了我正在访问的是哪个进程。
\item 陪练的主动气泡模板写好了，调用它的 \code{notify()} 却没有任何地方调用过，所以气泡从不出现。函数的每条测试都通过，因为没有一条测试问「谁调用它」。
\item 军师里留了一个未定义变量，控制台每秒抛一次 \code{ReferenceError}。实现改动时删掉了它的定义，留下了引用。
\end{itemize}

这三条都不是读代码读出来的，只有真的把页面打开、真打一局才看得见。

\subsection{验收要在真浏览器里真打一局}

我的做法是加两层检查，都不进 \code{npm test}——需要浏览器的检查不该当成必过门。

第一层是接线检查（\code{wiring.test.js}）。\code{app.js} 里每个 \code{\$('id')} 都必须在 \code{index.html} 或 \code{app.js} 自建的元素里存在，死函数清单必须恰好是两个已知遗留，面试题要求的每项能力都必须找得到入口。它第一次运行就抓出一处指向已删除元素的残留引用。

第二层是冒烟测试：无头浏览器从营地选人、逐回合出招、一直打到结算，断言页面渲染出伙伴卡、对局有结果、控制台零报错。这一层也误报过，一次报「最长连续无可点 14 次」，查下去是动画播放期间按钮本来就被禁用——那 14 次量的是动画时长，不是死锁。

\subsection{验收的另一半是核对口径}

检查只能验证断言本身，验证不了断言在数什么；有几处缺陷的代码完全正常，错的是口径。

玩家补位的那一回合本来就不该出招，却被计成一次「引擎兜底」，方向恰好让对手 agent 显得比实际更差。犹豫判定用的是「距第一次悬停的墙钟时间」：我在火花上停了一下，然后移去对方面板操作了 13 秒，回来碰了「防御」，界面就弹出「你在火花和防御之间停留了 13 秒」——那 13 秒我根本没在看这两个选项。信号要量的是花在这上面的时间，不是经过了多少时间。这两个例子不会让任何测试失败，只能逐条核对分子分母才能发现。

还有一类要读文字才看得出来。README 里写着「模型不参与伤害计算，也不决定对手出招」，而代码里对手的出招正是模型从引擎给出的合法行动表里选的——全仓库没有一条测试会去读 README。这类错处只能对着产物一条条重算：文档引的是某次运行的数字，代码又走了一轮之后那些数字全部失效，而声明还写着「可从产物复算」；我专门做了一遍全量核对，清出来的错处里有好几条属于这一类。

\subsection{检查本身也要被检查}

玩家文案里不许出现「启发式」「枚举」「分支」这类内部词。我为此写了禁止词表检查，写完先做负向验证：把表里的词植入一句玩家可达的文案，测试必须失败；移除，测试必须通过。

这一步暴露出一个原本看不出来的缺口：检查取局内提示时没有传事件参数，那条理由的正文根本不在覆盖范围内；第一次修补也错了，手工造一个事件参数传进去，负向验证立刻戳穿。最后换成静态扫描，逐行取 \code{coach/} 下的中文字面量对词表，不依赖运行时路径，随即又扫出四处真泄漏。检查写完之后，检查本身还要过一遍同样的关卡。
