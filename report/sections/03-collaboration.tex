\section{协作与验收}

使用子 agent 并行实现，我负责架构、验收与关键修复。全项目出现最多的一类问题是：代码看着对、测试全绿、功能根本没有生效——下面四个实例都不是读代码发现的，只有实际跑起来才看得见。

\begin{itemize}[leftmargin=1.5em,itemsep=0.12em,topsep=0.25em]
\item 服务端漏了静态资源白名单里的新模块 \code{rules.js}，\code{/rules.js} 返回 404，\code{app.js} 的 import 图整体失败，页面元素没有渲染出来。
\item 陪练的 \code{notify()} 写完了，全仓库没有调用点：主动气泡从不出现（后来补上了调用点）。
\item 军师里留了一个未定义变量，每秒抛一次 \code{ReferenceError}，浏览器日志里攒了 75 条。
\item 敌方补位「决定了却无人提交」：换宠选好、存进变量就返回，玩家那条路径又拒绝替它提交，界面永久冻结在「正在出招…」。
\end{itemize}

验收因此换成两层检查。第一层是 \path{wiring.test.js}：\code{app.js} 里每个 \code{\$('id')} 都要在 \code{index.html} 或 \code{app.js} 自建的元素里存在，死函数清单必须恰好是两个已知遗留，面试题要求的每项能力都必须找得到入口；它第一次运行就抓出一处指向已删除元素的残留引用。第二层是冒烟测试：无头浏览器真打一局，断言营地渲染出伙伴卡、对局打到结果、控制台零报错；它不进 \code{npm test}，因为需要浏览器的检查不该当成必过门；它也有假阳性，一次报「最长连续无可点 14 次」，查下去是动画播放期间按钮本来就被禁用。

\subsection{检查本身也要被检查}

术语检查写出来之后，我做了负向验证：把禁止词表里的词植入一句玩家可达的文案，测试必须失败；移除，测试必须通过。这一步暴露出一个原本看不出来的缺口——检查取局内提示时没有传事件参数，「明显策略错误」那条理由的正文根本不在覆盖范围内；第一次修补也错了，手工造一个事件参数传进去，负向验证立刻戳穿。最后换成静态扫描，逐行取 \code{coach/} 下的中文字面量对词表，不依赖运行时路径，随即又扫出四处真泄漏。

\subsection{代码是对的，错的是统计}

有一处缺陷代码完全正常，错的是统计口径：玩家补位的那一回合本来就不该出招，却被计成一次「引擎兜底」，方向恰好让对手 agent 显得比实际更差；同类的一处是犹豫判定用了墙钟时间，玩家中途去操作对方面板的 13 秒被算成「犹豫了 13 秒」。这类错误不会让任何测试失败，只能靠逐条核对分子分母才能发现。另一类更容易漏：交付里写下的「某方案没用」往往只对了一半——检索实验里最好的一臂确实没有显著赢过基线，但拆开四条臂能看到排序指标确实变好了。
